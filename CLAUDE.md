# CLAUDE.md

Guidance for Claude Code working in this repository.

## What this site is

A recipe site built with Jekyll and served by GitHub Pages from `main`. GitHub
builds Jekyll natively, so nothing in this repository deploys anything. The one
Actions workflow, `.github/workflows/ci.yml`, is a gate on *merging* rather than
on publishing: if it goes red on `main` the site still deploys, which is
intended. Do not add a deploy step to it.

Recipes are timed against one specific pressure cooker. Its model, wattage,
product link and companion app live in `_config.yml` under `appliance`. Read
them from there and reference them as `site.appliance.*`; never retype the model
name into a layout or a recipe.

## The one rule that outranks the others

**Every recipe page must stay importable by URL.** That is why this site exists
rather than being a folder of notes: a person pastes a recipe's link into a
recipe manager or an appliance app and the whole recipe arrives filled in.

If a change would improve how a page looks but degrade its structured data, the
structured data wins.

## The schema contract (hard requirement)

Every recipe page emits exactly one `schema.org/Recipe` object as JSON-LD,
generated by `_layouts/recipe.html` from the recipe's front matter. The visible
page is built from those same fields in the same pass, so the two cannot drift.

This shape is a hard requirement. Do not drop a field to simplify a layout, and
do not add one without checking it against the published vocabulary first.

### Where the field list comes from

The vocabulary is defined by <https://schema.org/Recipe>, published from
<https://github.com/schemaorg/schemaorg>. The machine-readable definition is
`data/releases/<version>/schemaorg-current-https.jsonld` in that repository —
read it there rather than trusting a blog post or this table, and rather than
trusting the rendered website, which is not always reachable from a sandbox.

The field list below was checked against **release 30.0**, and
`rake schema:drift` re-checks it quarterly rather than leaving that to memory.
It reads a clone of the vocabulary and asserts that no property emitted here has
gained a `schema:supersededBy`, that the `NutritionInformation` key list is
unchanged, that every `suitableForDiet` value is still a member of
`RestrictedDiet`, and that `Vocabulary::CHECKED_RELEASE` still names the newest
release. A failure opens an issue rather than reddening a build nobody watches.

The properties it checks are gathered from the built pages, not from a list kept
beside them, so this table cannot drift away from what the layout emits. The six
below that no recipe sets yet are the exception, and are listed in
`Contract::SUPPORTED_WHEN_SET` for exactly that reason.

`Recipe` inherits from `HowTo`, `CreativeWork` and `Thing`, so 148 properties
are technically valid on it. Most describe things a recipe page has no honest
answer for. What follows is what this site emits and, just as importantly, what
it refuses to.

### Supported but empty unless a recipe sets them

The layout emits these only when the front matter provides them. None is set
today. Add the data rather than adding markup.

| JSON-LD key | Front matter | Why it is empty |
|---|---|---|
| `video` | `video` | No recipe has one filmed yet |
| `license` | `license` | The repository is MIT; recipe content declares no licence of its own yet |
| `isBasedOn` | `is_based_on` | Set it when a recipe is adapted from a named source |
| `sameAs` | `same_as` | Set it when a recipe is also published elsewhere |
| `aggregateRating` | `rating` | **Only from real, recorded ratings** |
| `review` | `reviews` | **Only from real reviews** |

`aggregateRating` and `review` are the two that invite fabrication. A rating a
site awards its own recipe is dishonest, and search engines discard the whole
block as a self-serving review when they detect it. Leave them absent until
there is something real to record.

### Deliberately not emitted

- **`step`** (from `HowTo`). It is live, not superseded, and it means the same
  thing as `recipeInstructions`. Emitting both would repeat all eleven
  `HowToStep` objects, and a consumer that reads both properties and
  concatenates them would import a recipe with every step twice — a direct
  breach of the one rule at the top of this file. `supply` is duplicated in the
  same way and *is* emitted, because the asymmetry is real: a doubled
  ingredient list is obvious and harmless, a doubled method is a broken recipe.
  If an importer is ever seen double-counting ingredients, `supply` is the
  first thing to drop.
- **`ingredients`, `steps`, `reviews`, `awards`, `isBasedOnUrl`** and the other
  superseded spellings. Emitting a superseded property alongside its
  replacement is how a recipe ends up with two disagreeing ingredient lists.
- **The remaining ~96 `CreativeWork` properties** — `award`, `commentCount`,
  `contentRating`, `educationalUse`, `interactionStatistic`, `teaches`,
  `typicalAgeRange`, `wordCount` and so on. A recipe page has no honest value
  for them. An invented one is worse than an absent one, because a field that
  is present is believed.

### The six rules that break silently

These are the ways the contract gets violated by accident. The full reasoning
for each is in [README.md → The import contract](README.md#the-import-contract);
keep the two documents in agreement.

1. Images are **absolute** URLs in the JSON-LD, **relative** in `<img>` tags.
2. Every step is a `HowToStep` carrying both `name` and `text`.
3. Steps restate their appliance session (`continues: true`).
4. `prepTime + cookTime == totalTime`.
5. Every step's `url` anchor resolves to a matching `id` on the rendered `<li>`.
6. Ingredients are flat strings — quantity, unit and item on one line.

An importer fetches the JSON-LD away from the page and reads each step in
isolation. Rules 1 and 3 both follow from that, and both fail silently rather
than erroring.

Some importers are AI-assisted and can read a page with no structured data at
all. Clean JSON-LD is not what unlocks the import — it turns a guess into a
straight read, which is what keeps the appliance settings intact.

## The three documents

Each is written for a different reader, and they must stay in agreement — a
rule changed in one is changed in all three in the same pull request.

| File | Written for |
|---|---|
| `README.md` | someone looking at the repository: what it is, plus the full front-matter reference |
| `CONTRIBUTING.md` | someone about to change something: how to add a recipe, and what review expects |
| `CLAUDE.md` | this file — Claude Code working in the repository |

`CONTRIBUTING.md` deliberately does not restate this file. Where it needs a
detail that is already tabulated, it links to the README section rather than
copying it, so there is one place for each fact to go stale.

Those links are checked: `test/sources/documentation_test.rb` resolves every
relative anchor across the markdown files against the headings that actually
exist. Renaming a heading therefore fails the checks rather than quietly
sending readers to the top of the file — so rename freely, and fix what the
failure names.

Every test is generated by iterating `_recipes/*.md`, so no test names a recipe
or asserts one of its values. Adding a recipe adds its assertions; deleting one
takes them away. A rule that only holds for a particular dish does not belong in
the suite.

## Adding a recipe

Copy any existing file in `_recipes/`, rename it, and edit the front matter. The
filename becomes the URL: `_recipes/dal-tadka.md` → `/recipes/dal-tadka/`.

**Never write HTML in a recipe.** If a recipe needs something the layout cannot
express, extend the layout so every recipe gains it.

The step fields and their meanings are tabulated in
[README.md → Step fields](README.md#step-fields). Write `text` for a
`continues: true` step in lowercase, starting mid-sentence — the layout prepends
the appliance context.

### Filling in the derived fields

Four fields describe the dish rather than transcribe it, so they have to be
worked out per recipe. Copying them from another recipe is worse than leaving
them out, because a wrong number is believed and an absent one is not.

- **`nutrition`** — add up the ingredient weights and divide by the yield.
  State the serving size as a weight, and use `nutrition.note` to say it is an
  estimate and to name whatever dominates the numbers. Almost always that is
  the salt, the added fat, or both.
- **`estimated_cost`** — the ingredient cost for the whole pot, not per
  serving. Round up. It is an estimate, and the front matter comment should say
  which shops it is an estimate for.
- **`diets`** — claim only what the ingredient list actually supports, and
  check the compound ingredients before claiming anything. Commercial
  asafoetida is usually cut with wheat flour, which is why the masala rice is
  not labelled gluten-free; ghee, paneer, curd and butter each rule out
  `VeganDiet`. When a claim depends on which brand the cook buys, leave it off
  and explain in `notes`.
- **`alternate_names`** and **`disambiguating_description`** — the names the
  dish is genuinely known by, and the near neighbour it gets confused with.
  Both exist so a search engine and a reader can tell this dish from a similar
  one, so a vague answer is no answer.

`updated` is the modification date. Bump it when the method or the quantities
change, not when a typo is fixed.

## How recipes are written

These conventions are the site's voice. They are also documented for
contributors in [README.md → How these recipes are written](README.md#how-these-recipes-are-written)
and [CONTRIBUTING.md → The house voice](CONTRIBUTING.md#the-house-voice);
match them, and update all three places together if they change.

- **Calibrated for one cooker.** Timings assume the cooker named in
  `site.appliance`. Where another pressure cooker would differ, say so and give
  the adjustment rather than staying silent.
- **Every step names its function, level and duration** so the reader is never
  guessing which button to press.
- **Weights, not cups.** Grams and millilitres. In a sealed pot the ratio of
  grain to water decides the result, and a cup is not a reliable measure.
- **Failure modes up front.** Where a step commonly goes wrong — a Burn warning
  from an unscraped base, spices scorching on a high setting — say what happens
  and why, at the point where it matters.

## Allergens and diets

Every recipe declares both, because "can I eat this" is asked before the
ingredient list is read, not after.

**Diets** are `diets:` entries carrying a visible `label` and the schema.org
`RestrictedDiet` value emitted as `suitableForDiet`. There are exactly eleven
valid values — `LowFatDiet`, `VegetarianDiet`, `VeganDiet`, `HinduDiet`,
`GlutenFreeDiet`, `KosherDiet`, `LowLactoseDiet`, `LowSaltDiet`,
`DiabeticDiet`, `HalalDiet`, `LowCalorieDiet`. Anything else is silently
meaningless to a consumer. `HinduDiet` is claimed where a recipe is beef-free,
which is a fact about composition. `HalalDiet` and `KosherDiet` are *not*
claimed, because they depend on how ingredients were sourced and prepared, which
a recipe cannot know.

**Allergens** reference `_data/allergens.yml` by `id` and never by name:

```yaml
allergens:
  present:
    - id: peanuts
      note: Cooked into the rice, so they cannot be picked out.
  may_contain:
    - id: gluten
      note: Only through the asafoetida, which is usually cut with wheat flour.
  note: An optional caveat for the whole recipe.
```

The layout derives the "free from" list by subtracting what a recipe declares
from the fourteen, so the three lists always add up and adding an entry to the
data file makes every recipe claim *less*, never more — the safe direction for
the edit to fail in.

The list is Annex II of Regulation (EU) No 1169/2011 because it is a strict
superset of the US "Big 9" (FALCPA 2004, plus sesame via the FASTER Act, in
force since 1 January 2023). Celery, mustard, sulphites, lupin and molluscs are
declarable in the EU, UK, Canada and Australia/NZ but not by the FDA, which is
why `us:` names the US wording only where the two differ.

**schema.org has no allergen property.** This was checked against the
vocabulary dump, not assumed: the only term matching `allerg` is
`AllergiesHealthAspect`, which classifies the subject matter of a health
article. Google's recipe rich result does not consume one either. So allergens
go into the two places that can carry them honestly — visible prose, which is
what Fresco's AI-assisted import actually reads, and plain-text `keywords`
("contains milk", "may contain sulphites"), which is a real `Recipe` property
of type `Text`. Do not invent `hasAllergen`, and do not borrow
`additionalProperty`: its domain is `Product`, `Offer`, `Place` and the value
types, not `CreativeWork`, so not `Recipe`. A made-up property is dropped by a
strict JSON-LD processor and believed by a lenient one.

## Images

The full workflow, including the multi-image and per-step forms, is in
[README.md → Images](README.md#images). The parts that are easy to get wrong:

- **Resize and recompress before committing.** Roughly 1600 px wide and under
  ~500 KB. Git keeps every version of a binary forever, so an unprocessed phone
  photo bloats the clone permanently and cannot be undone by deleting it later.
- **Strip EXIF.** Phone photos can carry GPS coordinates, and this repo is
  public.
- **Always write `image_alt`** — it is what a screen reader announces.
- The hero crops to 4:3 and index thumbnails to 1:1, so keep food away from the
  extreme edges.

The first two are checked by `test/sources/assets_test.rb` — size, width, EXIF,
and images no recipe points at — because they are the rules that cannot be
fixed after the fact. Everything before the commit is still yours to get right:
the checks can tell you a photo is 3 MB, not that it is the wrong photo.

## Building and verifying

```
bundle config set path 'vendor/bundle'
bundle install
bundle exec rake
```

`bundle exec rake` is the whole verification story: it builds the site and runs
every check, cheapest first, stopping at the first set that fails. Run it before
proposing a change, and quote what it printed rather than saying it passed.

- `rake test:sources` — the recipe files as written; no build, milliseconds
- `rake test:import_contract` — one `jekyll build`, then the JSON-LD, the step
  anchors, the allergen arithmetic and html-proofer over the output
- `rake test:browser` — Chromium over the built site; needs Node, which it
  installs on demand into `test/browser`

Two tasks are deliberately *not* part of that default, and never gate a pull
request:

- `rake schema:drift` needs a clone of `schemaorg/schemaorg`, which a
  contributor has no reason to have; the task prints the exact clone command
  when it cannot find one. Run quarterly by
  `.github/workflows/schema-drift.yml`.
- `rake links:external` reads the internet. Rate limits, transient 503s and
  hosts that block CI ranges produce failures that have nothing to do with the
  change under review, and a red check a contributor cannot fix teaches
  everyone to ignore red checks. Run weekly by
  `.github/workflows/external-links.yml`. Internal links stay in
  `test:import_contract`, where they are fast and deterministic.

Both open an issue on failure rather than reddening a build nobody watches.

`vendor/`, `.bundle/`, `_site/` and `test/browser/node_modules/` are gitignored
— do not commit them.

`Gemfile.lock` **is** committed, so every machine and every CI run installs the
same tree. The `Gemfile` puts no version constraint on `github-pages`, so
without the lock a fresh resolve floats and a bad upstream release breaks a
build on a commit that changed nothing. Note this is deliberately the opposite
of GitHub's own Jekyll setup instructions, which tell you to ignore it; the
reasoning is recorded on issue #23. When a gem changes, commit the regenerated
lock in the same pull request as the `Gemfile` change. Dependabot proposes
those bumps monthly and grouped, which is only useful *because* the lock is
committed — see `.github/dependabot.yml`. `test/browser/package-lock.json`
is committed for the same reason.

`.ruby-version` pins 3.3.4 because that is what GitHub Pages runs, per
<https://pages.github.com/versions.json>, alongside `github-pages` 232 and
Jekyll 3.10.0. Re-read that file before changing the pin; it is the only
authority for the number. The macOS system Ruby is 2.6 and cannot install this
dependency tree at all.

### What the checks do not cover

Everything in the old manual list is now asserted — Liquid warnings,
`datePublished`, absolute image URLs, per-step anchors, the allergen
subtraction, `prepTime + cookTime == totalTime`, `supply` against
`recipeIngredient`, the two widths, images that actually loaded. What is left
needs judgement rather than a browser:

- **Whether a number is right rather than merely well-formed.** The nutrition
  figures, the cost, and whether a diet claim matches what is actually in the
  pot.
- **Whether a photograph is the right photograph**, well cropped and genuinely
  processed. The checks catch a 3 MB file, not a bad one.

A built page can also be pasted into the
[Schema Markup Validator](https://validator.schema.org/) or Google's
[Rich Results Test](https://search.google.com/test/rich-results), which catch
malformed JSON-LD — the usual reason an import fails without saying why. Worth
doing when `_layouts/recipe.html` changes: the checks assert the shape this site
emits, the validators know the whole vocabulary.

## Traps this repo has already hit

Each of these cost real debugging time and none is discoverable from the source.

- **`jekyll serve` rewrites `site.url` to localhost.** An incorrectly absolute
  URL then resolves anyway and the bug hides. Verify URL-sensitive changes with
  `jekyll build`, not `serve`.
- **The `github-pages` gem supplies a default theme.** It overrides this site's
  CSS and has broken the build outright with `Invalid US-ASCII character` from a
  Sass partial. `theme: null` in `_config.yml` must stay, and it overrides any
  advice from a general-purpose Jekyll skill or tutorial that suggests setting a
  theme.
- **`jekyll-seo-tag` reserves `site.social`** for a differently shaped hash.
  Social links therefore live under `maintainers`, grouped by person.
- **schema.org itself may be unreachable.** A sandboxed session can be blocked
  from `schema.org` and `developers.google.com` by an egress proxy, which makes
  it tempting to guess at a property name. Clone
  <https://github.com/schemaorg/schemaorg> instead and read the release JSON-LD
  — the vocabulary is the same, and GitHub is usually reachable when the
  website is not.
- **`jekyll-seo-tag` emits its own `BlogPosting` JSON-LD block.** The Recipe
  block is the *second* `<script type="application/ld+json">` on the page —
  index accordingly when validating.
- **Liquid has no `push` filter.** To build a list, capture a delimited string
  and `split` it.
- **`contains` is a Liquid operator, so it cannot be a front-matter key you
  read.** `page.allergens.contains` parses as a comparison; the build prints a
  syntax warning and renders nothing where you expected a list. The key is
  therefore `present:`, while the visible heading still reads "Contains".
- **A recipe missing its closing `---` still builds, silently and wrongly.**
  Jekyll's front-matter regexp needs a terminator; without one the whole file is
  content, `page.data` is empty, and — the part that makes it hard to spot —
  Jekyll auto-titles the document from its filename, so `gajar-halwa.md` still
  renders `<h1>Gajar Halwa</h1>` and an index card. The page just quietly loses
  its description, dates, diets, allergens and every time. Splitting the file on
  `---` in a checker does not catch this either: what follows is still valid
  YAML. Assert on the *built* page instead — that a field only front matter can
  supply, such as `datePublished`, is actually present in the JSON-LD.

## Front-end conventions

- **No external requests.** Icons are inlined SVG; there are no CDN scripts,
  webfonts or stylesheets. Nothing on a page should break because a third party
  went away.
- **Progressive enhancement.** The copy-link button is injected by script only
  where the clipboard API exists; without it the plain URL stays visible rather
  than leaving a control that silently does nothing.
- Editorial serif look on a warm paper palette, driven by the custom properties
  at the top of `main.css`. Add colours as tokens there rather than inline.

## Git workflow

- Develop on a branch; never commit directly to `main`.
- Keep pull requests modular — one concern each. Stack them when work builds on
  work that is not merged yet, basing each branch on the previous one.
- A merged PR cannot carry new work. Restart the branch from the latest `main`
  and open a new PR instead.

## Accuracy

State what was verified and what was not. Where a detail cannot be checked —
an exact in-app menu path, a vendor's current behaviour — write around it and
say so, rather than producing something plausible. A confident invention is
worse here than an admitted gap, because nobody re-checks a sentence that reads
as settled.
