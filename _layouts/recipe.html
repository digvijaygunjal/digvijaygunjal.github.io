--- layout: default --- {%- comment -%} One pass, two outputs. Everything below is derived from the recipe's front matter and then used twice: once for the schema.org/Recipe JSON-LD an importer reads, once for the page a person reads. Deriving both from the same variables is what stops the two from drifting apart. Two behaviours here exist purely because of how importers work: * URLs in the JSON-LD are absolute, because the importer fetches the structured data away from the page it came from; * every step restates its appliance session, because importers read each step in isolation. {%- endcomment -%} {%- comment -%} Ingredients: flatten the display groups into one list. `recipeIngredient` and `supply` are both built from this, so a group heading can never leak into the structured data. {%- endcomment -%} {%- assign flat_ingredients = "" | split: "" -%} {%- for group in page.ingredients -%} {%- assign flat_ingredients = flat_ingredients | concat: group.items -%} {%- endfor -%} {%- comment -%} Images: `image` accepts one path or a list. So the declaration below is emitted twice in the two places that can carry it honestly — as visible prose, which is what Fresco's AI-assisted import actually reads, and as plain-text `keywords`, whose own definition is "keywords or tags used to describe some item". What is deliberately NOT done: inventing `hasAllergen`, or borrowing `additionalProperty`, whose domain is Product, Offer, Place and the value types — not CreativeWork, so not Recipe.
